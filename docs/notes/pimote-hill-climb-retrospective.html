Hill Climb Retrospective: Building the Persona Hub

What it took to land the danny-ocean hub, and the documentation that would have made it a straight line.

Key takeaways
  • Three attempts were needed: a git-repo hub, then nested real personas, then the correct shape (top-level personas symlinked into a persona folder).
  • Both dead ends trace to undocumented pimote semantics, not to bad tooling: persona folders behave as leaves for real children, symlinks inside them are still walked, and the scan registry lags manual filesystem changes by up to ~30 seconds in waves.
  • Two short documents (a folder-model concepts doc and a hub recipes doc) plus two small tools (rescan and move persona) would have collapsed the whole climb to one attempt.

1. The core result

The finished topology, as the folder model now reports it:

/home/alenna/repos/
├── danny-ocean/                 persona  ← the hub
│   ├── AGENTS.md                Danny Ocean: crew lead, hub rules
│   ├── memory.md
│   ├── rusty-ryan      -> ../rusty-ryan          (symlink)
│   └── livingston-dell -> ../livingston-dell     (symlink)
├── rusty-ryan/                  persona  (canonical home)
│   ├── AGENTS.md
│   └── memory.md
└── livingston-dell/             persona  (canonical home)
    ├── AGENTS.md
    └── memory.md

The folder tree shows danny-ocean as a persona with two shortcut children, and both members as personas at their canonical paths. Sessions can start at any of the three folders.

2. The hill climb, attempt by attempt

Attempt 1: git-repo hub rejected

Shape. oceans-eleven/ as a git repository with an AGENTS.md, two relative symlinks to the new personas, and a commit.

Reasoning. The only hub example in the installation is “Ide hub”: a git repo whose members are symlinked in. I generalized from that one precedent.

Outcome. Discovery worked perfectly on the first try — the model showed a code hub with two persona members. The failure was interpretive, not mechanical: the user wanted the hub itself to be a persona. One plausible example was not enough to infer the intended taxonomy of hub shapes.

Attempt 2: real personas nested inside the persona undone

Shape. Deleted the git hub, created the danny-ocean persona, then mved the two real persona folders physically inside danny-ocean/.

Outcome. Three distinct symptoms appeared:

  • danny-ocean was discovered, but with children: [] — the walker does not descend into persona folders for real subfolders.
  • The persona registry kept listing the members at their old top-level paths that no longer existed.
  • After the paths went stale and were dropped, the new nested locations never registered at all.
Near-miss diagnosis. From the first stale read I almost concluded “persona folders are leaves, full stop.” That conclusion was too broad. Attempt 3 proved symlinks inside a persona folder are walked. Inference from one polluted observation nearly wrote a wrong rule into my memory notes.

Attempt 3: canonical homes + symlinks inside the persona kept

Shape. mv both members back to /home/alenna/repos/, then create relative symlinks ../rusty-ryan and ../livingston-dell inside danny-ocean/.

Outcome. The registry converged in waves: first the members reappeared at top level but Danny dropped off the list, then roughly twenty seconds later the full correct topology settled. Final verification against the folder tree confirmed the shape in section 1.

3. What each dead end taught

# Rule discovered Evidence
1 Persona folders are leaves for real subfolders. Nested personas are invisible: not walked, not registered, not startable via session tools. danny-ocean showed children: [] while containing two persona folders on disk.
2 Symlinks inside a persona folder are discovered, as shortcut children pointing at canonical entries. Final tree shows danny-ocean/rusty-ryan via shortcut with the persona entry resolved.
3 The scan registry is eventually consistent. Manual mv/ln converge in waves over up to ~30 seconds; tool calls broadcast folders_changed immediately. Stale old paths shown, then dropped; new paths appeared late; Danny briefly vanished from the persona list.
4 pimote_create_persona errors on an existing folder name. There is no move, rename, or adopt operation. Tool spec; also why attempt 2 had to be raw mv instead of a supported operation.
5 One example is not a taxonomy. “Ide hub” demonstrates the code-hub shape only; a persona hub is a different, undocumented recipe. Attempt 1 was rejected by the user despite matching the only visible precedent.

4. Why hill climbing happened at all

  1. No concepts document for the folder model. Scan roots, canonical paths versus occurrences, nature detection (persona front matter, git detection), leaf behavior, and shortcut walking were all inferable only by experiment.
  2. No recipes for hub shapes. The difference between a code hub (git repo + symlinks) and a persona hub (persona + symlinked member personas) was never written down. I picked the wrong one and only the user’s corrections revealed the distinction.
  3. Terse tool docs. The pimote_create_persona description documents its errors and template, but says nothing about leaf semantics, symlink members, or what happens to manually moved persona folders.
  4. No force-rescan or move tooling. With no way to ask the model to re-discover, the only way to learn lag semantics was to mutate the tree and poll. Each poll cycle cost a wait, and stale reads actively misled the diagnosis.
  5. Cold-start knowledge. My memory.md was empty at session start. Every lesson in section 3 is knowledge this installation already exercised somewhere — the watcher, the walker, the broadcast — but nothing had captured it in a form an agent reads before acting.
The pattern. Each wrong step was cheap (minutes), but the cost compounds: three restructurings, several verification waits, one near-wrong memory note, and two user corrections. Documentation converts that recurring cost into a one-time writing cost.

5. Documentation that would have prevented it

5.1 A folder-model concepts doc

One page, roughly this outline:

  • Scan roots and how discovery walks them.
  • Entries versus occurrences: canonical path is identity, occurrences are reach paths.
  • Nature detection: persona front matter in AGENTS.md, git repo detection, hub detection via members.
  • Walk rules per nature: code folders walk fully; persona folders walk only for symlinks; real children of personas are invisible.
  • Consistency: tool calls broadcast folders_changed; manual edits converge via the watcher within ~30 seconds, in waves; expect stale reads immediately after mutations.

5.2 A recipes doc for topologies

Short, copy-pasteable recipes with expected folder_tree output as a golden example:

  • Persona hub (what we built): member personas at top level via pimote_create_persona, relative symlinks inside the hub persona’s folder, hub rules in its AGENTS.md prompt.
  • Code hub (“Ide hub” shape): git-initialized folder, symlinked repos, repo members gitignored, persona members symlinked and committable.
  • Anti-patterns with symptoms: nesting real personas (invisible members), expecting instant registry updates after mv.

5.3 Per-tool behavioral notes

  • pimote_create_persona: collision behavior, exact template written, the folders_changed broadcast, and that it only creates — moving is the operator’s problem.
  • pimote_folder_tree: reads a cached registry, not a fresh walk; freshness guidance (“wait 30s after manual changes”).
  • pimote_start_session: requires a known folder path; nested-but-undiscovered personas cannot be targeted.

5.4 Where the docs should live so agents actually read them

  • An AGENTS.md in the manager’s cwd (or a pimote-docs skill) holding only a vision line and a lookup table pointing at the docs above. Per this installation’s own convention: maps, not containers.
  • Distill my memory.md lessons into those docs. Memory is tribal and per-installation; docs are authoritative and portable.
  • Embed one-line hints in tool outputs. A collision error could read: “folder exists; delete it first, or pick another name. Persona folders are leaves — symlink member personas instead.” That single sentence would have prevented attempt 2 entirely.

6. Tooling gaps worth closing

Gap Suggested tool What it prevents
No way to force discovery pimote_rescan — trigger re-discovery, return the delta Guess-and-wait polling cycles; near-miss diagnoses from stale reads
No supported move/rename pimote_move_persona — move with registry invalidation built in Raw mv plus wave-lag confusion (attempt 2 and 3)
Hub membership is hand-rolled symlinks pimote_add_member / pimote_remove_member — create or drop the symlink and broadcast Undiscovered members; wrong-link mistakes
Docs are far from the error site Hint strings in tool errors and success outputs Wrong-shape attempts that only user corrections catch

The cheapest high-value step is the pair of docs (5.1 and 5.2) plus the hint strings (5.4). The new tools are nice-to-have; the concepts and recipes are what turn a three-attempt climb into one attempt.
