Client Performance Audit

Svelte 5 + SvelteKit PWA — algorithmic complexity, streaming hot paths, main-thread saturation, network timing, bundle weight.

Scope: client/src at v0.16.0-rc.7 · static analysis + production build measurement

Key takeaways
  • Two hot paths scale quadratically with transcript size: live subagent deltas deep-clone the whole transcript per delta, and live tool output re-converts its full buffer through ANSI-to-HTML per delta. Both sit on the main thread and degrade exactly when the app is busiest — mid-run.
  • The bash output path re-encodes its entire accumulated buffer per delta to recompute a byte count the store already tracks.
  • Message content blocks are keyed by array index while the subagent projection splices blocks into the middle, so each insertion rebuilds the DOM tail of the message (markdown re-parse, highlight reset).
  • ~120 KB (gzip) of rarely-needed code ships eagerly: the voice-call stack and highlight.js core load at startup on every route; CodeMirror is correctly lazy.
  • The async discipline is otherwise strong: restores run in parallel, the composer is optimistic, search is debounced and epoch-guarded, and timers/observers are cleaned up consistently. The defects are concentrated in per-event work, not in orchestration.

Scope and method

The audit reads every non-test file under client/src with focus on the four requested classes: algorithmic complexity, missed batching, awaited network calls between UI transitions, and main-thread saturation. It adds bundle measurement from a production vite build (chunk sizes quoted below are from that build). Costs are stated in terms of transcript length n, content blocks per message b, delta count d, and folder/session counts f/s.

Streaming hot paths

HighS1 — Each subagent content delta deep-clones the whole transcript

client/src/lib/subagent-content.ts:114 → client/src/lib/stores/session-registry.svelte.ts:388

When a subagent streams live content, the delta lands in applyProjectedEventToTranscript, which runs per event:

// session-registry.svelte.ts:384
const { confirmed, pending } = confirmedTranscriptRows(transcript);
const projected = applySubagentContentEvent({ messages: confirmed.map((row) => row.message), ... }, event);
transcript.messages = [...projected.messages, ...pending.map((row) => row.message)];
transcript.messageKeys = [...confirmed.map((row) => row.key), ...addedKeys, ...pending.map((row) => row.key)];

// subagent-content.ts:114
const messages = cloneMessages(state.messages);   // {...m, content: m.content.map({...c})} for EVERY message

Per delta this maps and filters all n messages twice, deep-clones every message and every content block (cloneMessages), locates the operation with a nested findIndex scan (O(n·b)), and rebuilds both the messages and keys arrays. The common case routes here: the parent assistant message finalizes (its message_end arrives) before the child starts streaming, so streamingMessage is null and applyProjectedEventToStreaming declines. A run with d deltas therefore performs O(n·d) allocations plus a full displayEntries re-diff and a full toolResultUsageIndex re-index per delta (each sees a new messages array identity). With a 1000-message transcript and thousands of deltas, this is hundreds of MB of short-lived allocations, GC pressure, and main-thread stall — the audit's worst finding.

Fix: apply the delta in place — clone only the target message and its block, replace that one slot in messages/messageKeys, and keep row identities stable so the keyed each and downstream deriveds diff O(1) instead of O(n).

HighS2 — Live tool output: full ANSI→HTML conversion and full DOM replace per delta, uncapped buffer

client/src/lib/components/BoundedOutput.svelte:60, 47 · client/src/lib/components/ToolCall.svelte:393 · client/src/lib/stores/session-registry.svelte.ts:1866 
// BoundedOutput.svelte
let lines = $derived(text.split('\n'));                       // O(n) per delta
<pre ...>{@html ansiToHtml(displayText)}</pre>               // full convert + innerHTML replace per delta

// session-registry.svelte.ts:1866 — no cap, unlike bash output's 256 KB bound
call.partialResult += upd.content;

Every tool_execution_update appends to an unbounded string, then BoundedOutput re-splits all lines, runs the full buffer through ansi-to-html, and replaces the <pre> contents. Total work is O(n²) in final output size with no throttle — unlike code fences, which are throttled to 100 ms (see S7). A verbose tool streaming 1 MB across 2000 deltas converts ≈1 GB of text cumulatively and forces 2000 full DOM rebuilds, plus a per-delta scrollHeight read in the auto-scroll effect (forced layout). Bash executions take the same render path with the buffer capped at 256 KB — still ≈128 MB of cumulative conversion at the cap.

Fix: cap partialResult like bash output; render ANSI through a throttled incremental highlighter (trailing 100 ms, flush on tool_execution_end); append text nodes instead of replacing innerHTML.

MediumS3 — Bash live output re-encodes the whole buffer per delta to recompute a tracked number

client/src/lib/stores/session-registry.svelte.ts:257, 2342 
// appendBoundedBashOutput, run per delta:
const currentBytes = utf8ByteLength(current);   // TextEncoder().encode(current) — full buffer, every delta
...
this.bashOutputBytes.set(outputKey, bounded.bytes);   // the count is tracked right here

utf8ByteLength encodes the entire accumulated output on every bash_execution_update, up to the 256 KB cap — O(n²) bytes of UTF-8 encoding per execution, while bashOutputBytes already carries the exact count from the previous delta. A chatty command emitting 1000 deltas encodes ≈128 MB cumulatively.

Fix: pass the stored byte count into appendBoundedBashOutput and add only the delta's encoded length.

MediumS4 — Child-view streaming deltas copy every content block of the streaming message

client/src/lib/stores/session-registry.svelte.ts:497 
const content = streaming.content.map((block) => ({ ...block }));   // per delta, all b blocks
...
attachment.streamingMessage = { ...streaming, content, ... };

The root-path message_update handler mutates one block in place; the child-view reducer copies all b blocks and rebuilds the message object per delta — O(b·d) allocations where O(d) suffices. Cheap when a message has few blocks; noticeable for tool-heavy child messages with many blocks and frequent deltas.

Fix: copy only content[update.contentIndex]; reuse the other block references.

MediumS5 — Every finalized message rescans and deep-clones the transcript for subagent projection

client/src/lib/stores/session-registry.svelte.ts:1725–1734, 1840–1843 · client/src/lib/subagent-content.ts:160–179 
session.projectedSubagentContent = hydrateSubagentContent(session.messages, session.projectedSubagentContent.active);
session.messages = [...session.projectedSubagentContent.messages];

hydrateSubagentContent clones every message and content block, then walks all n·b blocks hunting for active subagent entries — on every message_end and custom_entry, plus two full-array copies. Per finalized message this is O(n), so a session accumulates O(n²) copy volume over its lifetime. Constants are small and events are per-message rather than per-delta, so it stays Medium — but removing it also removes most of the remaining allocation pressure around S1.

Fix: scan only the newly arrived message (projection is append-driven; existing active entries are already in active) and clone just the affected row.

MediumS6 — Content blocks are keyed by array index while the projection splices into the middle

client/src/lib/components/Message.svelte:316 · client/src/lib/subagent-content.ts:127 
{#each visibleContent as block, i (`native-${i}`)}

// subagent-content.ts:127 — insertion, not append:
else content.splice(Math.min(event.contentIndex, content.length), 0, block);

Keys are native-0, native-1, …. When subagent_content_start splices a block in at index k, every block after it inherits a shifted key, so Svelte destroys and recreates that whole tail: TextBlock re-runs its markdown parser from zero, ThinkingBlock/ToolCall reset, and the DOM churns. This compounds with S1 (insertions typically accompany a starting subagent run).

Fix: key blocks by stable identity — toolCallId/operationId where present, otherwise an insertion-ordered id minted once per block.

Rendering and main thread

MediumR1 — Find-in-conversation rescans the entire transcript on every keystroke

client/src/lib/components/MessageList.svelte:206 · client/src/lib/conversation-find.ts 
const findMatches = $derived.by(() => {
  if (!findQuery.trim() || !session) return [];
  return findInConversation(session.messages, findQuery.trim());   // toLowerCase() over every text block
});

While find is open, each keystroke lowercases and scans every text block of every message — O(transcript bytes) per keystroke, on the input handler's task. A 500 KB transcript at typing speed means multiple MB of scanning per second, plus re-runs whenever any message mutates mid-run. Matches are also unbounded: a common query can allocate tens of thousands of match objects.

Fix: debounce ~150 ms, cache the lowercased text per block (invalidate on message identity), and cap matches per block.

LowR2 — Sticky-target tracking reads layout for every user row, every frame, during streaming

client/src/lib/components/MessageList.svelte:222–236, 317–320

updateStickyTargets is rAF-coalesced, but each tick calls getBoundingClientRect() on every user-message row (transcriptPositions), and it is triggered by a per-row ResizeObserver plus a tick().then(...) effect that fires whenever displayEntries changes — i.e. continuously during streaming. Reads are batched per frame, so cost is O(user rows) per frame rather than a thrash spiral; on long transcripts with hundreds of user rows this is measurable scroll-jank alongside the streaming render itself.

Fix: compute the sticky row from scroll offsets and cached row heights (the virtualizer/list inner already knows them) instead of per-row getBoundingClientRect, or restrict measurement to rows near the viewport top.

LowR3 — Stick-to-bottom reads computed style on every scroll write

client/src/lib/stick-to-bottom.svelte.ts:199 
const { scrollBehavior } = getComputedStyle(scrollElement);

The follow animation writes scrollTop every frame while content grows; each write first reads getComputedStyle, forcing style recalculation. One read per frame is tolerable, but the value changes only when CSS changes.

Fix: cache scroll-behavior per scroll element and invalidate on ResizeObserver/media changes.

LowR4 — Duplicate derived text joins in Message

client/src/lib/components/Message.svelte:120, 139–141 
let textContent = $derived(visibleContent.filter(...).map(...).join('\n\n'));
let userText  = $derived(getUserText(message));
let customText = $derived(getUserText(message));   // identical computation, again

userText and customText are the same fold over all text blocks, recomputed (alongside textContent) on every content mutation — so a streaming assistant row joins its full text three times per delta. Constants are small (V8 string concat is fast) but it is pure duplicate work on the hottest component.

Fix: compute one joinedText derived and slice the three consumers off it.

Network and async

MediumN1 — Stale autocomplete responses can overwrite fresh ones

client/src/lib/components/CommandAutocomplete.svelte:42–48 
const seq = ++serverRequestSeq;
if (currentMode === 'fileRefs' && completeFileRefs) {
  serverItems = await completeFileRefs(currentQuery);   // ← returns BEFORE the seq guard
  return;
}
if (currentMode === 'args' && completeArgs) {
  serverItems = await completeArgs(currentCommandName, currentQuery);   // ← same
  return;
}
...
if (seq !== serverRequestSeq) return;   // guard exists only on the fallback path

The two injected-callback paths await and assign without the staleness check that the direct connection.send path applies. A slow earlier request (e.g. fd scan on a large repo) resolves last and replaces the list for the newer prefix — a visible correctness/perf hybrid: wrong suggestions plus wasted work.

Fix: check seq !== serverRequestSeq before both early-return assignments.

LowN2 — Reconnect backoff has no jitter

client/src/lib/stores/connection.svelte.ts:687–698 
this.reconnectDelay = Math.min(this.reconnectDelay * 2, 30000);

Exponential backoff caps at 30 s but is deterministic: after a server restart, every tab and device retries in lockstep, and each attempt triggers a full restore fan-out (replay buffers, profile reconcile). With a handful of clients this is minor; with many it is a synchronized herd against a server that is re-attaching sessions.

Fix: multiply the computed delay by 0.5 + Math.random() (full jitter).

LowN3 — Session selection waits on two extra round-trips

client/src/lib/stores/session-registry.svelte.ts:2845 
await refreshSessionMetaAndCommands(sessionId);
if (shouldSwitch) sessionRegistry.selectSession(sessionId);

switchTo already runs optimistically before the awaits (good), but final selection — and anything keyed to it — waits for open_session + get_session_meta + get_commands. Other paths already fire this refresh without awaiting (line 3144).

Fix: drop the await; select immediately and let the meta refresh land in the background.
Verified clean in this area: reconnect restores fan out with Promise.all, not serially (connection.svelte.ts:469–479); prompt, steer, and bang-bash all render optimistic state before the await and restore the draft on failure; dashboard search is server-authoritative, debounced (folder-store.svelte.ts:184–187), and generation-guarded; autocomplete requests are debounced at 200 ms with timer cleanup.

Lists, dashboard, folder store

LowL1 — visibleFolders is an uncached getter doing O(total sessions) work per read

client/src/lib/stores/folder-store.svelte.ts:119–133 
get visibleFolders(): FolderInfo[] {
  const list = this.folders.filter(...);
  const recency = (folder) => Math.max(0,
    ...(this.sessions.get(folder.path) ?? []).map((s) => toTimestamp(s.modified)),
    ...openActivity.filter(...).map(...),
    folder.lastActivity ?? 0);
  return [...list].sort(...);
}

Every read filters all folders, re-parses ISO timestamps for every session of every folder, and sorts. FolderList caches it in one $derived (FolderList.svelte:168), which bounds the damage — but any additional read (a second consumer, a length check in a template) re-runs the whole fold, and every session event re-triggers it. Date.parse per session per recomputation is avoidable.

Fix: convert to a memoized $derived over folders/sessions/showArchived/queryMatchPaths, and cache parsed timestamps on arrival.

LowL2 — Virtualized rows re-measure on every render

client/src/lib/components/FolderList.svelte:285–293 
instance.measureElement(node);
return {
  update: () => instance.measureElement(node),   // runs on every props re-run of the row
  ...
};

The action's update hook re-measures each visible row whenever its parameters object is rebuilt — which is every render pass of the list. ~15 visible rows × getBoundingClientRect after DOM writes can force repeated layouts per update. TanStack already tracks size via its own observer once measureElement is wired in the action's init.

Fix: drop the update hook; keep init-time measureElement and let ResizeObserver handle growth (tags, subtitles, expansion).

LowL3 — Dashboard renders a 210 KB icon at 90 px

client/src/lib/components/Dashboard.svelte:99 
<img src="/pwa/icon-512.png" ... class="size-[90px] ..." />

The landing page transfers the 512 px icon (210,404 bytes) to draw a 90 px avatar; icon-192.png (36 KB) is already shipped, and badge-96.png (2.4 KB) exists too. First-visit cost on mobile WAN.

Fix: use icon-192.png (or export a 180 px WebP, ≈8 KB) with explicit width/height for CLS.

Bundle and load

MediumB1 — The voice-call stack ships eagerly on every route

client/src/routes/+layout.svelte:17 · chunk GcOiwt3i.js 
import '$lib/stores/voice-call-store.js';   // side-effect import at boot, layout level

The side-effect import pulls the voice/WebRTC/analyser seam graph statically into the layout chunk: the 155 KB (50 KB gzip) voice chunk is referenced directly by the layout and session-route nodes. Voice is an occasional feature; its store subscription could attach after first user intent (or after requestIdleCallback) via dynamic import.

Fix: lazy-import the voice store on the first voice affordance (mic button render or voice event) instead of at boot.

LowB2 — highlight.js core is in the eager startup graph

client/src/lib/components/TextBlock.svelte:3 → smd-renderer → code-highlight → syntax-highlighter · chunk 1GF6WFHw.js

Every TextBlock statically imports the highlight pipeline, so hljs core (67 KB raw, 22 KB gzip, shared by all route nodes) loads at startup — needed only when a message actually contains a code fence. The 700 KB (241 KB gzip) CodeMirror + language chunk, by contrast, is correctly reachable only through the editor dialog's dynamic import (verified in the emitted graph).

Fix: dynamic-import smd-renderer/code-highlight on the first fence (or after idle), keeping the smd parser itself static.

InfoB3 — Startup weight baseline

Eager JavaScript for a session-route cold load (measured from vite build): layout node 82 KB + session node 194 KB + shared UI chunk 259 KB + voice 155 KB + hljs core 67 KB + shared runtime 61 KB + misc 27 KB ≈ 845 KB raw / ~210 KB gzip, plus three small woff2 subsets. Lazy: CodeMirror chunk 700 KB. Applying B1 and B2 removes ≈55–75 KB gzip from the critical path. The static-adapter shell is empty (ssr = false), fonts are self-hosted variable subsets with unicode-range (browsers fetch only latin — confirmed three small woff2 files in the build), and the service worker's fetch handler intercepts only /_share POSTs, so it never delays navigation.

Checked clean

  • TextBlock streaming — writes only the slice since the last write, ends the parser once, cancels pending highlight timers on teardown (TextBlock.svelte:27–54).
  • Code-fence highlighting — throttled to one pass per 100 ms with trailing flush; the right pattern S2's ANSI path should copy.
  • Connection lifecycle — stale-socket guards everywhere, pending requests rejected on replace/close, restore fan-out parallel, replays cursor-based; duplicate-tab id guard via BroadcastChannel.
  • Composer flows — optimistic user message and transient bash UI before the await, draft restore on failure, connection-loss treated as "outcome unknown" rather than double-send.
  • Folder search — server-authoritative, debounced, epoch/monotonic-token guarded with a bounded stale-retry budget.
  • Virtualization — stable path keys, overscan 5, per-row ResizeObserver measurement, lazy session-list fetch limited to rendered rows.
  • Transcript DOM — keyed each at row level with stable message keys; row usage summarization indexed once per snapshot instead of per row.
  • ImagePreview — loading="lazy" + decoding="async".
  • Listener hygiene — every onMount listener, observer, and timer found in Panel, ActiveSessionBar, BranchExplorer, MessageList, InputBar, SwipeableCard has a matching removal.
  • Service worker — no precache (intentional, network-required app), fetch handler scoped to the share-target endpoint, per-client focus map bounded by tab count.
