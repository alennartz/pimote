Wire Protocol Performance Review

What a protocol-change allowance would buy: the egregious items, the genuinely low-hanging fixes, and what is already right.

Scope: shared/src/protocol.ts, server wire paths (ws-handler, session-surface, event-buffer), client consumption

Implementation status: all six findings below are addressed. Image bytes now use content-addressed HTTP refs backed by a 64 MiB memory LRU and an XDG disk cache capped at 1 GiB; large resyncs use ordered message, branch-ID, active-operation, and in-flight-message fragments; WebSocket compression is enabled without context takeover; streaming updates batch at 16 ms (up to 128 events); metadata and commands ride lifecycle/open responses; and observer fan-out shares serialized events. The three items under “Structural, not low-hanging” were not changed.
Verdict: the protocol's shape is sound — cursors, epochs, mid-run resync partials, and windowed folder listings are well designed. The initial review found that the egregious items were about payload, not shape: megabyte-scale inline base64 images inside transcript content, whole-session snapshots in a single JSON frame, and zero wire compression. Server-side delta micro-batching also reduced the per-frame fixed costs.

Egregious

1 · Payload Inline base64 images ride inside transcript content
shared/src/protocol.ts:184 — MAX_IMAGE_BASE64_LENGTH = 4 MB

Prompt images and tool-result images travel as base64 data-URL strings inside PimoteCommand and inside PimoteAgentMessage content blocks. Every image is then replayed on every open_session, copied into every snapshot and replay buffer entry, held in the client's reactive session state, and re-parsed by the browser per render as a data URL. One 4 MB image inflates the socket frame by 4 MB of base64 plus the JSON escaping around it — and it re-ships on each attach and resync.

Implemented: POST /api/images accepts image bytes and returns a content-addressed /i/<sha256> path. Prompt commands carry that path, and transcript plus tool-result blocks carry the same reference. A 64 MiB memory LRU backs a 1 GiB XDG disk cache; legacy native data URLs remain accepted.

2 · Payload Whole-session snapshot in one JSON frame
server/src/ws-handler.ts:1294 — { state, messages }; full_resync same shape

Open, reconnect-without-valid-cursor, and mid-run resync all deliver the complete transcript as one text frame. The client JSON.parses it synchronously on the main thread; a long session means a multi-megabyte parse stall at exactly the moment the user is waiting for first paint. Reconnect restores fan out one full snapshot per previously-open session, in parallel.

Implemented: large snapshots send a start envelope, UTF-8-safe serialized message fragments, plus separate branch-ID, active-operation, running-tool, and in-flight-message fragments. The client parses each fragment incrementally and emits one ordinary full_resync only after the snapshot completes. This keeps even one unusually large message out of a single frame without dropping history.

3 · Transport No wire compression
server/src/server.ts:253 — new WebSocketServer({ noServer: true }), permessage-deflate unset

Transcript JSON is highly repetitive and compresses roughly 5–10×. Today every replay frame crosses the WAN at full size. The CPU tradeoff that justifies leaving it off on a LAN does not hold for the PWA-over-internet case this project targets.

Implemented: the WebSocket server negotiates perMessageDeflate above 1 KiB with both context-takeover options disabled.

Low-hanging with protocol changes

4 · Frame density Micro-batch streaming deltas

Every text delta, tool-output chunk, bash chunk, and subagent content delta is its own frame, sent the moment it is mapped. A dense turn — one subagent run plus bash — produces hundreds of frames per second, and each frame costs a server send plus a client JSON.parse, dispatch, and Svelte flush. The client audit fixed the per-event work; the per-event overhead lives here.

Implemented: streaming events coalesce per observer socket for 16 ms, with a 128-event ceiling, into one event_batch. A non-streaming lifecycle event flushes the batch first. The client applies batched events in order.

5 · Round-trips Piggyback meta and commands on events

The client requests get_session_meta after agent_end, again after turn_end (the same turn, so two round-trips carrying the same answer), and after compaction; get_commands adds another round-trip on every session open. updateMeta then loops every session sharing the folder.

Implemented: turn_end carries persisted metadata; agent_settled covers aborts and runs without a turn end; compaction and session-replacement events carry metadata. Successful open_session responses carry metadata and commands, plus an initial snapshot for new sessions. The client no longer requests meta or commands after ordinary open or reconnect.

6 · Server CPU Serialize fan-out once, and stop stringify-scanning snapshots
ws-handler.ts:2475 sends JSON.stringify(event) per client; session-surface.ts:311 stringifies every snapshot message per message_end during an attach window

An event is stringified once per attached client; with several tabs or devices the same bytes are rebuilt N times. Separately, the snapshot-attach dedupe compares messages by full-JSON equality — two stringify calls per stored message per final event, inside a window that also streams.

Implemented: sendSlotEvent serializes one event once for all observers. Snapshot attachment builds a SHA-256 content-fingerprint index once, checks entry IDs when available, and avoids stringifying every snapshot message for each arriving final event.

Structural, not low-hanging

  • Wall-clock replay cursors (DR-077). The clock base exists so a cursor from a retired buffer resyncs safely instead of replaying wrong history. An epoch + monotonic sequence would remove clock dependence, but the current scheme is a deliberate correctness trade, not a perf defect.
  • Folder info awaited inline in open_session — resolveFolderInfo can run cold git probes before the snapshot ships, delaying replay delivery. Folder rows already arrive via folders_changed deltas, so the open response could ship the snapshot first.
  • Streaming events are not buffered — reconnecting mid-stream falls back to a full resync by design (streaming deltas are live-only). A bounded tail of recent deltas in the buffer would shrink resyncs, at the cost of buffer memory and complexity. Documented tradeoff; fine to keep.

Already right

  • Cursor-based replay on reconnect (no redundant snapshot when the cursor is valid), with a safe snapshot_required fallback and stale-cursor invalidation.
  • Windowed, epoch-guarded folder listings with reconciled deltas and monotonic order tokens — the pattern finding #2 should copy.
  • Mid-run full_resync partials (streaming message + running tool ids) instead of synthetic events.
  • Child views with independent cursors, keeping subagent traffic out of root replay positions.
  • Optimistic composer with clientMessageId-stamped echoes — no round-trip in the send path.
