# DR-053: Unified folder model — code/persona taxonomy, sparse discovery, folder-resident persistence

## Status

Accepted

## Context

Pimote's folder space was described by three overlapping mechanisms: the repo index walk (discovery) merged with a curated project registry (DR-045), and multi-repo hub folders that existed only as registry entities — invisible to the walker by design (DR-046). This worked while "a project" was the only thing worth pointing at, but the 1.0 substrate (user-defined teams of agents) needs one model that answers "what folders do I have and what are they?" for code and persona folders alike, reached directly or through links. Keeping the repo walk, the registry, and hub special-casing as three parallel truths would have forced every new surface (manager tree tool, persona metadata, shortcut linkage) to reconcile them. The decision unifies discovery, classification, and linkage into a single folder model and makes the older mechanisms views over it.

> Supersedes DR-045 (Repo index orthogonal to curated projects), deleted at commit `7a525cb95e37c9a30ef5dc3e52d73a65fc13b37d`.
>
> Supersedes DR-046 (Multi-repo projects as hub folders with symlinks and a generated AGENTS.md), deleted at commit `7a525cb95e37c9a30ef5dc3e52d73a65fc13b37d`.

## Decision

**Taxonomy: two natures, decided by a marker.** A folder is a **persona folder** iff its `AGENTS.md` begins with a YAML front-matter block carrying a string `name:` key (the my-pi agent-definition format; body = persona prompt); else a **code folder** iff it has `.git`; else **skipped** and descended through. Marker wins over git when both are present. We rejected "any folder with an `AGENTS.md` is a persona" because pimote's own repo carries project instructions in its `AGENTS.md` — the marker must be an explicit agent definition, which also reuses one existing format instead of inventing vocabulary. We rejected a third "reference" folder kind and the orthogonal nature × linkage attribute model because linkage describes how the tree _reaches_ a folder, not what the folder _is_ — a shortcut is the same folder appearing again, not a wrapper. The strict marker (front matter must begin the file, `name` must be a string) is deliberate: a malformed or partial block degrades to git-fallback/skipped rather than silently minting a persona.

**Sparse discovery and identity by canonical path.** Discovery starts only at configured scan roots (never the manager's working directory — the manager folder is not part of the tree), descends through skipped folders with no depth bound, and stops at included ones. An included folder's top-level out-of-tree symlinks are **shortcuts** that restart discovery at their target; symlinks met during skipped descent are ordinary folders. Identity is the canonical real path, visited once per scan: the tree carries **occurrences** (reach paths) pointing at shared **entries** (identity). We rejected per-occurrence identity because a persona is one ongoing conversation no matter how many ways the tree reaches it — and visit-once gives cycle safety for free. We rejected keeping a depth-bounded walk (the old repo walker) because depth bounds hide nested folders of interest behind an arbitrary constant. Accepted costs: completed entries reuse their first-discovery children (later occurrences inherit reach paths nobody re-derived), in-progress cycle hits emit leaf back-references (children hidden at that point), and occurrence paths record reach, not identity — followed-symlink and skipped segments survive inline by design.

**Hubs are self-describing git repos.** Hub materialization adds `git init` and a `.gitignore` listing the member symlink names (symlinks and generated `AGENTS.md` unchanged from DR-046), so a hub classifies as an ordinary code folder and its member repos surface as shortcut occurrences — the hub model falls out of the folder model by construction. This supersedes DR-046's key consequence that "hubs are never walker-discovered repos, invisible to the repo index": that invisibility was fine when the registry was the only consumer, but under the unified model it would have made hubs permanent special cases in discovery, the repo view, and the manager tree tool. We rejected keeping registry-only hubs (that permanent special case) and rejected copying/nesting repos into the hub (duplicates state; symlinks keep members the single source of truth). Member validation stays index-members-only, so the symlink API cannot become arbitrary-link creation.

**Curation keys on canonical paths.** Favorite/archive/order/tags attach to the entry's canonical path (carried forward from DR-045). A moved folder orphans its curation state — recorded, ignored on merge. We rejected move-tracking or content-derived stable IDs: they need reconciliation machinery whose cost exceeds the value of surviving a move, and canonical paths double as the natural identity key for shortcuts, sessions, and sources. The registry store stays at `<state>/projects` with the legacy `multiRepo` key (and `projectSourcesDir` / `project-sources` dir for sources) read-compat — no migration, at the price of seams that must be retired later.

**Persona persistence is folder-resident artifacts.** A persona persists by leaving artifacts in its own folder — today a `memory.md` linked from its `AGENTS.md` — not through conversation or session persistence machinery. Each conferral starts fresh; continuity lives in the folder. This re-derives rather than inherits DR-047: the manager stays ephemeral _because_ memory is folder-resident, with no special manager case. We rejected persistent persona/manager sessions (files, replay, resume) as heavyweight machinery for a "ask, act, done" surface. Persona memory and manager lifecycle are named future work, not part of this decision's implementation.

**Vocabulary converges on "folder".** The rename runs through the published `@pimote/sdk` seam as a documented 0.x breaking bump (0.14.0→0.15.0) with no compatibility type aliases — "project" survives nowhere in product vocabulary (the FULL-RENAME variant recorded in the plan). We rejected the stable-SDK carve-out because it would keep "project" alive in the one seam external sources compile against and force permanent translation at every boundary; a clean break while the API is 0.x is cheaper than a bilingual seam.

## Consequences

- The tree is now one truth: `pimote_folder_tree`, the repo view (code entries + git status), and the curated list are all views over the same scan; no second recursive walker exists.
- Hubs gain a real `.git` and appear in the complete code-folder repo view (`list_repos`) — intentional. Disband deletes the hub's `.git` along with the folder; member repos survive (symlinks are unlinked, never followed). Pre-existing git-less hubs remain listed as legacy rows and are never backfilled with `git init` on listing or startup.
- Occurrence reach paths are unpinned for shared children, and cycle points show leaf occurrences — consumers must treat `entry.path` as the only identity.
- Symlink mechanics remain a portability constraint (fine for the self-hosted Linux deployment).
- Bootstrapping: no folder classifies as persona until its `AGENTS.md` gains the front-matter marker; a marker-less, git-less `AGENTS.md` includes nothing.
- Curation survives root reorganizations and discovery swaps (it hangs off identity, not reach) but not on-disk moves of the folder itself.
- `scanFolderModel` is pure and on-demand; TTL caching stays at the repo-index adapter boundary, so call-rate behavior is unchanged.
- Future revisit points if circumstances change: the canonical-path curation key (if moves turn out common), the strict marker grammar (if real personas keep failing to parse), and DR-047's ephemerality (when manager lifecycle is designed properly — the trigger is any need for cross-visit manager memory, which must then decide between folder artifacts and session persistence).
