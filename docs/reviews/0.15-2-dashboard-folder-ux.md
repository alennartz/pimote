### 2. One unreadable or vanished hub symlink breaks the whole folder listing

- **Category:** code correctness
- **Severity:** warning
- **Location:** `server/src/folder-registry.ts:212-236` (`readHubLinks`), called from `viewOver`
- **Status:** resolved

Every `list()` and `listLazy()` call runs the hub-link probe. The probe tolerates only `ENOENT`/`ENOTDIR` on `readdir`; `readlink` has no catch. Any other error rejects the whole view: `list_folders`, deltas, `update()`, and `addMember`. Triggers include a symlink removed between `readdir` and `readlink` (`ENOENT`), a symlink replaced by a file (`EINVAL`), and `EACCES` on one hub directory. Listings are not serialized with `removeMember` or user shell edits, so the race is real. Before this change the listing never read hub directories. A per-entry failure must skip that link or hub, not fail the dashboard.

### 3. `removeMember` does not validate `hubPath`, and `addMember` accepts any listed folder as a hub

- **Category:** code correctness
- **Severity:** warning
- **Location:** `server/src/folder-registry.ts:604-612`, `650-683`
- **Status:** resolved

`removeMember` runs `readHubLinks([hubPath])` on any client-supplied path. If any symlink there resolves to the given `memberPath`, it unlinks it and strips seeded lines from that directory's `AGENTS.md` and `.gitignore`. A wire client can therefore unlink any symlink the server user can write. This contradicts the DR-053 guard the plan keeps ("no arbitrary symlink operations"); the guard is enforced only on add. `addMember` checks only that `hubPath` is some non-missing row, so any code or persona folder can gain symlinks and a managed block in its own `AGENTS.md`. The UI gate (`members !== undefined || shortcutCount > 0`) is not a server invariant. Both methods need the same hub-eligibility check.

### 4. Source-listed persona folders appear in pickers, but the server rejects them

- **Category:** code correctness
- **Severity:** warning
- **Location:** `server/src/folder-registry.ts:692-704` (`discoveredNatures`), `332-336` (member `nature` fallback), `client/src/lib/components/FolderCreatorWizard.svelte:83-86`, `client/src/lib/components/HubMembersDialog.svelte:24`
- **Status:** resolved

`mergedFolders` lists out-of-tree source personas as rows, so they reach `folderStore.folders` and both member pickers. `discoveredNatures` reads only the scan tree and `repos.listLazy()`, so `createHub` and `addMember` reject them with `Unknown folder: …`. Members and `repos` resolve nature only through `scanned`, so such a member would report `nature: 'code'` and get a `missingRepo` placeholder. The membership rule ("any discovered folder-model entry") and the row source disagree. One function must own "discovered entry → nature", including `sourcePersonas`.

### 5. Member candidates come from the paginated window cache

- **Category:** code correctness
- **Severity:** warning
- **Location:** `client/src/lib/components/FolderCreatorWizard.svelte:83-86`, `client/src/lib/components/HubMembersDialog.svelte:24`
- **Status:** resolved

`folderStore.folders` holds fetched `list_folders` windows (100 rows by default) plus rows merged from search and deltas. Archived rows appear only after "Show archived". Neither picker has search or pagination. With more folders than the fetched prefix, valid members cannot be picked, and the offered set depends on scroll and search history. The existing toolbar "Create hub…" avoids this by using `folderStore.repos` (`list_repos`).

### 10. Partial failure in `addMember` leaves disk and registry inconsistent

- **Category:** code correctness
- **Severity:** nit
- **Location:** `server/src/folder-registry.ts:614-640`
- **Status:** resolved

If the `.gitignore` write fails, the rollback unlinks the symlink but keeps the seeded `AGENTS.md` line. If `persist` fails after the disk changes, nothing rolls back and no change fires: the symlink and line stay on disk, the registry hub's `memberPaths` lacks the member, and clients see no delta. A retry then fails with `Duplicate member name`.

### 11. After `open_session` fails, Create re-sends the creation command

- **Category:** code correctness
- **Severity:** nit
- **Location:** `client/src/lib/components/FolderCreatorWizard.svelte:134-160`
- **Status:** resolved

The folder already exists when `open_session` fails, but the wizard stays on the text step with Create enabled. A retry sends the create command again and the server answers `EEXIST` ("Directory already exists"). The user cannot recover in the dialog. The created `folderPath` must be kept so a retry only re-opens the session.

### 12. `addMember` accepts members nested inside, or containing, the hub

- **Category:** code correctness
- **Severity:** nit
- **Location:** `server/src/folder-registry.ts:604-612`, with the skip rule in `readHubLinks` (`212-236`)
- **Status:** resolved

The only guard is `memberPath === hubPath`. A discovered folder deeper inside the hub gets a symlink that `readHubLinks` skips (target inside the hub), so it never shows in `members`; for a non-registry hub `removeMember` rejects it as "Not a member". An ancestor of the hub as member creates a symlink cycle on disk.

### 13. Persona seeding duplicated; core modules depend on `manager/`

### 15. The members dialog can reopen by itself

- **Category:** code correctness
- **Severity:** nit
- **Location:** `client/src/lib/components/FolderList.svelte:118-119`, `898-903`
- **Status:** resolved

The dialog is open while `membersHub` resolves, but only a user-initiated `onOpenChange` clears `membersHubPath`. If the row leaves `folderStore.folders` while the dialog is open (disband elsewhere, or a reconnect clearing the cache), the dialog closes but the path stays set. When a row with that path returns (refetch, or a hub recreated under the same name), the dialog reopens unprompted.
